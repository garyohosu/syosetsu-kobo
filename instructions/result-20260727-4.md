# AIエージェント間メール・ワーカーループ実装結果

## 実装概要

`mail/`へμITRON型のワーカーループを追加した。Pythonワーカーはメール待機中にAIプロセスを起動せず、
自分宛てのメールを1件だけ排他的に取得したときに、登録済みハンドラーまたは安全な引数配列のCLIを起動する。
正常終了後は`completed`へ戻り、失敗時はエラーを保存して再試行または`failed`へ遷移する。

## DBスキーマ変更

SQLite `PRAGMA user_version`を2へ更新し、既存`messages`表へ次を冪等に追加した。

`processing_status`、`attempt_count`、`last_error`、`processing_started_at`、`completed_at`、`updated_at`、
`conversation_id`、`parent_message_id`、`hop_count`、`escalation_sent`。既存メールは削除せず、処理状態は
`pending`、系列IDは`legacy-<message_id>`として移行する。接続は操作完了時に閉じる。

## 状態遷移・排他制御

`pending` → `processing` → `completed` または `pending` / `failed`。
既読フラグはこの状態とは独立して従来どおり保持する。

`BEGIN IMMEDIATE`内で`created_at, id`順に対象を選択し、`pending`から`processing`へ更新する。
更新件数を確認してコミットするため、複数ワーカーが同じメールを処理しない。

## 再試行・タイムアウト・回復

最大試行回数、処理タイムアウト、待機間隔、放置判定時間は`WorkerConfig`またはCLI引数で変更可能。
試行回数、最後のエラー、処理開始・完了・更新時刻を記録する。`recover`またはループ開始時の回復処理で、
一定時間以上`processing`のメールを`pending`へ戻す。Ctrl+C相当では停止イベントを設定し、現在の処理後に待機から終了できる。

## 無限往復防止

`conversation_id`、`parent_message_id`、`hop_count`を保持する。ハンドラーからの新規メールは系列情報を継承し、
`max_hops`超過時は処理を失敗終了して、任意に指定されたエスカレーション先へ通知する。固有のAI製品名は固定していない。

## CLI使用例

```bash
python mail/agent_mail.py worker-once --agent reviewer --timeout 60 --max-retries 3 --max-hops 10 --command python tools/handle_mail.py
python mail/agent_mail.py worker-loop --agent reviewer --interval 2 --stale-after 900 --command python tools/handle_mail.py
python mail/agent_mail.py recover --stale-after 900 --agent reviewer
python mail/agent_mail.py worker-status --agent reviewer
```

CLIのコマンドは`subprocess.run(..., shell=False)`で起動し、メール本文は標準入力へ渡す。本文をコマンドとして解釈しない。
