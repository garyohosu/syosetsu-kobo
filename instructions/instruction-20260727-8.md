# URSから複数企画案を生成・比較・選択する企画工程の実装

## 1. 目的

`SPEC.md v0.7`、`instructions/result-20260727-7.md`、既存のPythonオーケストレーター、対話型URS、AIエージェント間メールを基盤として、確定済みURSから小説の企画候補を複数生成し、比較・選択・確定できる最初の実働創作工程を実装してください。

今回の完了条件は、対話型URSから引き渡された版付き`URS.vNNN.md`を入力に、企画候補を独立した成果物として生成し、URS適合性、意外性、先読み欲求、既視感・模倣リスクを比較し、hantaniが短い操作で一案を選択でき、選択結果から非上書きの版付き`CONCEPT.vNNN.md`を確定して次工程へ引き渡せることです。

小説本文、試し書き、文章の改稿、文体調整を生成する場合はGeminiを担当とする既存方針を維持してください。今回の主対象は企画工程であり、本文執筆工程そのものは実装しません。

3. `AGENTS.md`、`CLAUDE.md`などのリポジトリ内指示があれば先に全文を読んでください。
4. 少なくとも次を読んで、既存契約と実装済み範囲を把握してください。

## 3. 必須設計

### 3.1 企画担当エージェント

- `agents/planner.md`を、URSから企画候補を作る正式な企画エージェント定義として実装または更新してください。
- エージェント定義には、役割、入力、出力、許可操作、禁止事項、次工程、アダプター、モデル、タイムアウト、合計試行回数を既存スキーマに従って記述してください。
- 企画担当は小説本文を執筆しません。確定済みURSを満たす作品コンセプト、中心的な葛藤、主人公の欲求、物語の推進力、独自性、読者が続きを読みたくなる理由を設計します。
- 企画担当はURSの確定事項を黙って変更せず、仮決定・未決事項を確定事項として扱いません。
- 参考作品の固有名詞、固有設定、固有場面、特徴的な表現や文体を再現しません。参考情報は「なぜ好きか」という抽象的な創作原理へ変換してください。

### 3.2 複数候補の生成

- 確定済み`URS.vNNN.md`から、既定3案の互いに明確に異なる企画候補を生成できるようにしてください。
- 候補数は設定またはCLIで変更可能にし、入力値を安全な範囲に検証してください。妥当な既定値と上限は実装根拠を`SPEC.md`へ明記してください。
- 各候補は最低限、次を含む構造化Markdownにしてください。
  - 候補IDと仮題
  - 一文コンセプト
  - 読者へ約束する中心的な読書体験
  - 主人公、目的、障害、賭けるもの
  - 中心的な人物関係
  - 舞台・世界の核
  - 物語を動かす仕掛け
  - 序盤の導入
  - 中盤を持続させる力
  - 終盤・結末の方向性
  - 「次を読みたい」と思わせる要因
  - URSの必須条件への対応
  - 意図的に採用しなかった要素
  - 未決事項、仮定、リスク
- 候補は別々のIDと成果物で保存し、再実行時に既存候補を黙って上書きしないでください。
- Geminiへ渡す長文は、既存の標準入力またはMarkdownパス・メールID・実行IDによる参照渡しを使ってください。URS本文、結合プロンプト、候補本文をコマンドライン引数へ載せてはいけません。

### 3.3 比較・監査

- 企画生成と企画評価は責務を分けてください。同じ生成結果を無批判に自己採点して採用する構造にしないでください。
- 各候補について、少なくとも次を比較可能な形で評価してください。
  - URS適合性
  - 必須条件と禁止事項
  - 意外性と独自性
  - 先読み欲求
  - 主人公の能動性
  - 長編または指定分量を支える持続性
  - 中盤がだれるリスク
  - 既視感・参考作品模倣リスク
  - 設定矛盾または実現困難な仮定
- 数値だけで合否を決めず、根拠、長所、弱点、改善案を記録してください。
- AIの推奨順位は提示してよいですが、最終選択はhantaniが行います。AI推奨を自動的に確定企画へ昇格させてはいけません。
- TBD-004〜TBD-006を今回の都合だけで全面解決しないでください。候補比較に必要な暫定尺度や停止条件を置く場合は、設定可能な仮仕様として明示し、未解決事項との境界を`SPEC.md`へ記録してください。

### 3.4 選択、修正、確定

- CLIまたは既存Python APIから、候補一覧、候補詳細、比較結果を取得できるようにしてください。
- hantaniが候補IDを短く指定して選択できるようにしてください。
- 「どれも選ばない」「再生成」「候補を基に修正」「保留」を区別してください。
- 選択前の候補、比較、AI推奨は正史にも確定企画にも反映しないでください。
- 選択・修正の履歴は追記型で保存し、旧候補や旧選択を消さないでください。
- 確定時に、選択候補と必要な修正を統合して版付き`CONCEPT.vNNN.md`を作成してください。確定済み版を上書きせず、再確定は新しい版にしてください。
- `CONCEPT.vNNN.md`には最低限、文書情報、参照URSの版とパス、選択候補と根拠、作品ブリーフ、一文コンセプト、読書体験、主人公、中心関係、舞台、葛藤、物語の推進力、構成方向、結末方向、必須・禁止条件、仮決定・未決事項、リスク、次工程入力を含めてください。
- 参照したURS版を固定し、後からURSの別版が作られても既存CONCEPTの根拠がすり替わらないようにしてください。

### 3.5 SQLite、メール、状態遷移

- 既存状態DBへ、企画セッション、候補、評価、選択・修正履歴、確定文書を追跡するための最小限のテーブルまたは列を、冪等な移行として追加してください。
- 作品ごとの進行中企画セッション、参照URS版、各候補ID、生成実行ID、評価実行ID、成果物パス、状態、作成・更新時刻を追跡してください。
- 中断後は、完了した候補生成を繰り返さず、未完了の評価または選択待ちから再開してください。
- URS確定時に作成済みの`urs-maker`から`planner`へのメールと同じ会話系列を引き継ぎ、企画の開始、比較完了、選択待ち、確定、次工程引渡しを追跡できるようにしてください。
- 通常の候補本文や評価全文を親Claude Codeへ中継しません。親へは状態、成果物参照、判断が必要な論点の要約だけを返してください。
- 次工程は既存仕様と実装を確認して設定してください。未実装の担当へ引き渡す場合も、エージェントID、期待入力、成果物参照を明示し、存在しない実働処理が完了したとは記録しないでください。

### 3.6 Geminiとダミーアダプター

- 企画の創作文生成はGeminiへルーティングしてください。Geminiの未導入、利用資格、認証、信頼設定、タイムアウト、非ゼロ終了、空出力、不正出力を既存分類で扱い、別AIへ無言でフォールバックしないでください。
- 現在確認されている終了コード55を成功扱いにしたり、特別に握り潰したりしないでください。
- 実Geminiを利用できない環境でも、決定論的なダミーアダプターで候補生成、比較、選択、確定、中断再開、次工程引渡しまで自動テストできるようにしてください。
- ダミー成果物を実Gemini生成物や利用者承認済み成果物と誤表示しないでください。実行記録へアダプター種別を残してください。
- 認証情報の入力、読取り、保存、コミットは行わないでください。

## 4. CLI

既存のJSON CLI規約と終了コードを維持し、少なくとも次に相当する操作を提供してください。名称は既存CLIとの整合を優先してよいですが、READMEと`--help`へ明記してください。

- 企画セッション開始
- 状態・進捗表示
- 候補一覧
- 候補詳細
- 比較結果表示
- 候補選択
- 選択保留
- 全候補不採用
- 再生成
- 選択候補への修正指示
- 選択・修正履歴
- CONCEPTプレビュー
- CONCEPT確定
- 中断・再開

長文の修正指示や追加資料はargvへ直接載せず、UTF-8 MarkdownまたはJSONファイルのパスで受け取れるようにしてください。短い候補IDや短い選択語だけをargvへ置くことは許可します。

## 6. 必須テスト

既存テストを維持したうえで、少なくとも次を自動テストしてください。

1. 版付き確定URSから既定3候補を生成する。
2. 候補ID、成果物、実行履歴が一意で、再実行時に上書きされない。
3. 各候補が必須項目を満たし、参照URS版を保持する。
4. 候補生成と評価の担当・実行記録が分離される。
5. URS適合性、禁止事項、意外性、先読み欲求、持続性、模倣リスクの比較根拠が保存される。
6. AI推奨だけでは候補が確定しない。
7. 候補選択、保留、全不採用、再生成、修正、確定を区別できる。
8. 選択・修正履歴が追記され、旧記録を失わない。
9. `CONCEPT.vNNN.md`が非上書きで版管理され、参照URS版を固定する。
10. 中断・再起動後に完了済み処理を重複せず、未完了地点から再開する。
11. メールの会話系列、作品ID、URS版、企画セッション、実行ID、候補IDを追跡できる。
12. Gemini失敗時に別AIへフォールバックせず、状態とエラーを保持する。
13. ダミーアダプターだけでURS確定後から企画確定・次工程引渡しまで完走する。
14. 10万文字超のURSまたは追加資料でもargv長が本文長に比例せず、本文断片を含まない。
15. 長文修正指示のパス横断、未知候補、別作品・別セッション混入、二重確定を拒否する。
16. 既存のURS、オーケストレーター、メール、Geminiテストがすべて成功する。

利用可能な環境では次も実行してください。

- Python全体のテスト
- `compileall`
- CLIのダミースモーク
- `gemini-doctor`
- 明示的な実Geminiスモークは、非機密の短文に限り1回だけ行ってよい
- `git diff --check`

実Geminiスモークが利用資格や信頼設定で失敗しても、ダミーを含む自動テストが成功していれば実装全体の失敗とはしません。ただし、実応答生成に成功したと偽らず、終了コード、分類、成果物の有無を報告してください。

## 7. 受入条件

- 確定URSから複数の異なる企画候補が生成され、候補・評価・選択が追跡できる。
- hantaniの選択なしに企画が確定しない。
- 選択候補から版付き`CONCEPT.vNNN.md`を非上書きで確定できる。
- 企画候補の創作生成はGeminiへルーティングされ、失敗時に無言の代替を行わない。
- 長文をCLI引数へ載せず、Windowsのコマンドライン長制限を回避する。
- ダミー環境で工程全体、中断再開、メール連携を再現できる。
- 既存機能、DB、メールCLI、URS、実行履歴との後方互換性を維持する。
- `SPEC.md`を実装結果に合わせて次版へ更新し、要求ID、受入条件、未解決事項、実装済みと未実装の境界を整合させる。
