# `QandA.md`全6問の回答を`SPEC.md`へ反映する作業指示書

## 1. 目的

`QandA.md`に整理された6件の未決事項について、本指示書に記載するhantaniの決定を正式回答として扱い、`SPEC.md`をv0.1からv0.2へ更新してください。

## 2. 作業開始前の確認

1. リポジトリ内の`CLAUDE.md`、`AGENTS.md`などの作業規約を探し、存在する場合は全文を読む。

3. `git status --short --branch`、現在のブランチ、直近のコミットを確認する。
4. 既存の未コミット変更を消去、上書き、巻き戻し、退避しない。
5. `SPEC.md`、`QandA.md`および本指示書を全文読む。
6. `instructions/instruction-20260727-2.md`が未実行の場合でも、本作業で同指示書のメールシステム仕様を代わりに追加しない。両作業の責務を分離する。

## 4. 正式回答

以下をhantaniの確定回答として扱ってください。別の推奨案へ置き換えたり、再質問したりしないでください。

### Q1／`TBD-001`: 対話型URSメーカーの対話相手

**回答: Q1の選択肢1を採用する。**

- MVPでは小説工房の内部、すなわち工房長であるClaude Codeとの対話によって`URS.md`を作成できること。
- ChatGPTなど外部AIとの壁打ちは必須にしない。
- 外部で行った壁打ちログ、メモ、既存回答は任意入力として取り込めること。
- 取り込んだ情報は出典を区別し、既に回答済みの質問を省略するために利用できること。
- 外部ログを取り込まなくても、全工程を開始・完了できること。
- 外部ログを無条件に正しい要求として確定せず、必要に応じてhantaniへ確認すること。

`TBD-001`を解決済みにし、該当内容をFR-001〜FR-010、入力仕様、URS工程、受入条件およびトレーサビリティへ反映してください。

### Q2／`TBD-007`: hantaniが承認する単位

**回答: Q2の選択肢4を採用し、既定値は選択肢1の「話（節）単位」とする。**

- 既定の承認単位は「話（節）」とする。
- 作品ごとに`URS.md`で、場面単位、話単位、章単位などへ上書きできること。
- `URS.md`に指定がない場合は話単位を使用すること。
- 承認対象の単位が完成するまでは案または承認待ちであり、正史へ確定しないこと。
- hantaniの明示的な承認後にだけ、対象単位を正史化し、台帳と嗜好モデルを更新すること。
- 承認単位を途中で変更する場合は、`URS.md`の改訂として変更理由と適用開始位置を記録すること。
- 過去に承認済みの単位へ、変更後の粒度を黙って遡及適用しないこと。

`STATE-002`、`FR-046`、`DATA-003`、`DATA-005`、関連する承認フロー、受入条件およびトレーサビリティを更新してください。

### Q3／`TBD-009`: `MyLike.md`の26作品の好きな点の聞き取り

**回答: Q3の選択肢1を採用する。**

- `MyLike_kousatsu.md`にある「URS作成時に優先して尋ねる質問」10項目を、対話型URSメーカーの初期質問キューへ組み込むこと。
- 一度に10問をまとめて提示せず、一問ずつ、選択肢、読み味や影響、推奨案、「今は決めない」、自由記入を含む既存の対話原則に従って聞くこと。
- 最初に「特に好きな上位5作品」を選んでもらい、各作品について好きな点を順次確認できること。
- 26作品すべてについて、最初から詳細回答を必須にしないこと。
- 既に分かっている情報や過去の回答は再質問しないこと。
- `MyLike_kousatsu.md`の分析は`AI推定`または`未確認仮説`として保持し、hantaniの回答で確認・修正された場合だけ確度を上げること。
- 「今は決めない」が選ばれた項目は創作開始を妨げず、作品案への反応から後で更新できること。

`FR-001`〜`FR-010`、`FR-018`、`SAFE-005`、嗜好データ仕様、質問順序、`AC-001`、`AC-003`およびトレーサビリティへ反映してください。

### Q4／`TBD-002`: 個別AIエージェントのモデル・CLI

**回答: Q4の選択肢1を採用する。ただし、通信と役割定義は最初からモデル・CLI非依存にする。**

- MVPの最初の動作確認はClaude Codeおよびそのサブエージェントを基本とする。
- MVP完了条件に、Claude、Codex、Gemini、Grokなど複数ベンダーの混在動作を含めない。
- 段階2で、他モデル・他CLIとの混在を検証すること。
- エージェントの役割定義、入出力ファイル、`agent_id`、結果形式に、Claude Code固有の会話機能を必須条件として埋め込まないこと。
- 子AI間の通常連絡を親Claude Codeが全文中継する構成を必須にしないこと。
- `instructions/instruction-20260727-2.md`で追加予定のSQLiteメール通信と矛盾せず、将来は独立したAI CLIをエージェントとして接続できる境界を保つこと。
- 使用したモデル、CLI、版、役割は実行記録へ残すこと。

この決定は「当面Claude Codeで検証する」という実装段階の選択であって、Claude Codeへの恒久的な製品依存を意味しません。`AI-010`、`NFR-010`、実行記録、MVPと段階2の範囲、受入条件およびトレーサビリティへ反映してください。

### Q5: MVPで「短い試作」工程を必須にするか

**回答: Q5の選択肢1を採用する。**

- 独立した複数バリアントの短い試作工程は段階2へ置く。
- MVPでは第1話の初稿提示を方向確認として利用する。
- `FR-022`および`AC-013`自体を削除せず、段階2の要求・受入条件として保持する。
- MVPでも、hantaniが明示的に依頼した場合に試作を行うことは妨げない。ただしMVP完了の必須条件にはしない。

現在の`SPEC.md`の段階分けと一致していることを確認し、「未決」または判断待ちという表現を解消してください。

### Q6／`TBD-008`: 複数作品の並行進行

**回答: Q6の選択肢1を採用する。**

- MVPで同時にアクティブに扱う作品は1作品だけとする。
- 保存構造は最初から`projects/<work-id>/`とし、作品を識別できる形を維持すること。
- 「続けて」「続きを書いて」など作品IDを省略した継続指示は、MVPでは唯一のアクティブ作品へ適用すること。
- 複数作品の同時進行、アクティブ作品の切替、曖昧な継続指示の解決は段階2以降とする。
- 将来複数作品へ拡張できるよう、作品IDをデータやパスから削除しないこと。

`TBD-008`を解決済みにし、対象範囲、状態管理、継続指示、保存構造、段階分け、受入条件およびトレーサビリティへ反映してください。
