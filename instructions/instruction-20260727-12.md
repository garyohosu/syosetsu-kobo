# 確定本文から正史・各種台帳を更新し、次章へ制作状態を引き継ぐ工程の実装

## 1. 目的

`kihitsugi.md`、`SPEC.md`、`instructions/result-20260727-8.md`（章・シーン設計と本文制作工程）、既存のPythonオーケストレーター、ストーリーバイブル・プロット工程、開発ループを基盤として、承認・確定済みの`CHAPTER-NNN.vNNN.md`だけを入力に、作品の正史と継続制作に必要な台帳を更新する工程を実装してください。

今回の完了条件は、確定本文から`CANON.vNNN.md`・`CHARACTER_LEDGER.vNNN.md`・`TIMELINE.vNNN.md`・`RESOURCE_LEDGER.vNNN.md`・`FORESHADOWING_LEDGER.vNNN.md`を生成し、台帳更新担当と独立整合性監査担当を分離した監査を経て、利用者の明示承認後にだけ版付きで非上書き確定でき、確定後に次章の`scene-planner`へ確定プロット・確定バイブル・正史・各台帳のパスを引き渡せることです。未承認の初稿・監査指摘・破棄された改稿を正史へ混入させてはいけません。

小説本文、試し書き、文章の改稿、文体調整を生成する場合はGeminiを担当とする既存方針を維持してください。台帳の抽出・要約・統合もGeminiが担当しますが、台帳更新担当は新規の創作文（本文）を書きません。今回の主対象は正史・台帳更新工程であり、本文執筆工程自体の変更は対象外です。

## 3. 必須設計

### 3.1 台帳更新担当エージェント

- `agents/canon-updater.md`を、確定本文・確定バイブル・確定プロット・直前の確定台帳から正史と5種の台帳草案を作る正式なエージェント定義として追加してください。
- 既存スキーマ（`agent_id`、`display_name`、`role`、`adapter`、`model`、`inputs`、`output`、`next_agent`、`allowed_operations`、`forbidden`、`timeout`、`max_attempts`）に従って記述してください。
- 台帳更新担当の創作文生成はGeminiへルーティングしてください。小説本文（試し書き・改稿含む）は書かず、確定済み情報の抽出・要約・構造化・差分統合だけを行います。
- 確定本文・確定バイブル・確定プロット・直前の確定台帳の内容を無断で変更・上書きせず、未承認の草案・監査指摘・破棄された改稿を参照source_pathにも正史にも混入させません。
- `forbidden`には最低限`write-prose`（本文生成の代替禁止）、`modify-upstream`、`auto-approve`、`execute-input`を含めてください。既存の`story-architect.md`・`prose-reviewer.md`等の`forbidden`に既にある`write-canon`は、台帳更新担当以外のエージェントに引き続き禁止として残してください。

### 3.2 独立整合性監査担当エージェント

- `agents/canon-auditor.md`を、台帳草案を確定本文・確定バイブル・確定プロット・直前の確定台帳へ独立照合する監査エージェント定義として追加してください。
- 台帳更新担当とは別の責務・別の実行記録とし、同じ生成結果を無批判に自己採点して確定させる構造にしないでください。
- 監査では最低限、人物、関係、知識、時系列、資源、能力、伏線、世界ルールの矛盾を確認し、対象箇所、根拠、判定、深刻度を記録してください。
- `forbidden`には最低限`write-canon`（台帳・正史の直接書き換え禁止）、`write-prose`、`auto-approve`、`modify-upstream`、`execute-input`を含めてください。
- AI監査だけで正史更新を確定してはいけません。監査結果は承認判断の材料であり、利用者の明示承認を経ない限り版付き成果物を作成できないことをコード側でも強制してください。

### 3.3 版付き成果物

- `kobo/canon.py`に`CanonManager`を実装し、確定済み章単位で次の5種の版付きMarkdownを、作品ストア配下の専用ディレクトリ（例: `store/works/{work_id}/canon/`）へ非上書きで保存できるようにしてください。
  - `CANON.vNNN.md`: 確定した出来事と世界状態
  - `CHARACTER_LEDGER.vNNN.md`: 人物の状態、関係、知識、目的
  - `TIMELINE.vNNN.md`: 出来事の時系列
  - `RESOURCE_LEDGER.vNNN.md`: 所持品、能力、資源、制約
  - `FORESHADOWING_LEDGER.vNNN.md`: 伏線の設置、進行、回収状態
- 既存の`STORY_BIBLE.vNNN.md`・`PLOT.vNNN.md`・`CHAPTER-NNN.vNNN.md`と同様、既存パスが存在する場合は上書きせずエラーにしてください。
- 版番号は作品単位で単調増加させ、各成果物の版が対応する章番号・参照した確定本文の版・参照した直前の確定台帳の版を、成果物本文のヘッダーとSQLite双方に記録してください。

### 3.4 固定参照と初回・継承

- セッション作成時に、確定本文（`CHAPTER-NNN.vNNN.md`とその版）、確定バイブル、確定プロット、直前の確定台帳（存在する場合）のパスと版を固定参照として記録し、以後生成中に別版へすり替わらないようにしてください。
- 第1章（当該作品で確定台帳が存在しない場合）は、空の台帳（各成果物が「まだ確定した出来事・人物・伏線がない」ことを明示した既定テンプレート）から開始してください。空欄を推測で埋めてはいけません。
- 第2章以降は、直前の確定版（`v(N-1)`）を継承し、今回の確定本文で新たに生じた差分だけを追加・更新する構造にしてください。台帳更新担当が既存確定内容を無断で書き換えないことを監査で確認してください。

### 3.5 SQLite、状態遷移、中断再開、二重確定拒否

- 既存状態DBへ、台帳更新セッション、生成物、監査、承認・却下履歴、確定文書を追跡するための最小限のテーブルを、`story_design.py`・`manuscript.py`と同様の冪等な`CREATE TABLE IF NOT EXISTS`で追加してください。
- 作品ごとの進行中セッション、対象章番号、参照した確定本文・確定バイブル・確定プロット・直前確定台帳のパスと版、生成実行ID、監査実行ID、成果物種別ごとのパス、状態、作成・更新時刻を追跡してください。
- 中断後の再開（例: `canon-resume`）は、完了済みの生成・監査を繰り返さず、未完了の監査または承認待ちから再開してください。
- 承認前の草案・監査結果を正史にも次章の参照にも反映しないでください。同一セッションでの二重確定（`canon_documents`相当の完了済みレコードがある状態での再確定）を拒否してください。
- 却下・修正指示は追記型で保存し、旧草案・旧監査を消さないでください。監査で矛盾が見つかった場合に台帳更新担当へ限定的な修正指示を送り、差分再監査を行う経路を、`manuscript.py`の初稿・監査・改稿・再監査と同様の構造で用意してください。

### 3.6 メール系列と次章への引き継ぎ

- 章確定時に`manuscript.py`の`finalize`が返す`next_stage_implemented:False`を解消し、確定本文からのメール系列（`writer`→`prose-reviewer`の会話系列、またはそれに連なる系列）を引き継いで`canon-updater`へ開始・監査完了・承認待ち・確定の各段階を送信してください。
- 確定時には、`works`テーブルの`current_agent`・`next_agent`・`status`を更新し、次章の`scene-planner`が`next_agent`として設定されるようにしてください（`story_design.py`のプロット確定時の引き渡しと同様のパターン）。
- 確定台帳の`scene-planner`への引き渡しメールには、確定プロット・確定バイブル・正史・4種の台帳それぞれのパスを明示してください。存在しない実働処理を完了したと記録しないでください。
- 通常の草案・監査全文を親Claude Codeへ中継しません。親へは状態、成果物参照、判断が必要な論点の要約だけを返してください。

### 3.7 Geminiとダミーアダプター

- 台帳更新の創作的な抽出・要約・統合はGeminiへルーティングしてください。Geminiの未導入、利用資格、認証、信頼設定、タイムアウト、非ゼロ終了、空出力、不正出力を既存分類で扱い、別AIへ無言でフォールバックしないでください。終了コード55を成功扱いにしないでください。
- 実Geminiを利用できない環境でも、決定論的なダミーアダプター（`--dummy`）で、生成・監査・承認・確定・中断再開・次章引き渡しまで自動テストできるようにしてください。
- ダミー成果物を実Gemini生成物や利用者承認済み成果物と誤表示しないでください。実行記録へアダプター種別を残してください。
- 認証情報の入力、読取り、保存、コミットは行わないでください。
- 長文（確定本文、確定バイブル、確定プロット、直前確定台帳、監査結果）をコマンドライン引数へ載せず、既存の標準入力またはMarkdownパス・メールID・実行IDによる参照渡しを使ってください。

## 4. CLI

既存のJSON CLI規約と終了コードを維持し、少なくとも次に相当する操作を提供してください。名称は既存CLI（`manuscript-*`、`story-*`）との整合を優先してよいですが、READMEと`--help`へ明記してください。

- 台帳更新セッション開始（対象章番号、対象作品を指定）
- 状態・進捗表示、中断・再開
- 生成物表示（草案／監査／修正／再監査／確定のいずれか種別指定）
- 承認
- 却下・修正指示（長文はファイルパスで受け取る）
- 確定（`CANON.vNNN.md`ほか4種を非上書きで確定）

長文の修正指示や追加資料はargvへ直接載せず、UTF-8 MarkdownまたはJSONファイルのパスで受け取れるようにしてください。短い章番号や短い判定語だけをargvへ置くことは許可します。

## 6. 必須テスト

既存テストを維持したうえで、少なくとも次を自動テストしてください。

1. 版付き確定本文から第1章相当で空の台帳を起点に5種の草案が生成される。
2. 第2章相当で直前の確定台帳（v1）を固定参照として継承し、差分だけが更新される。
3. 台帳更新担当と独立整合性監査担当の実行記録が分離される。
4. 監査が人物、関係、知識、時系列、資源、能力、伏線、世界ルールの矛盾根拠を保存する。
5. AI監査だけでは確定せず、利用者承認後にだけ`CANON.vNNN.md`ほか4種が非上書きで版付き確定される。
6. 却下・修正指示から台帳更新担当への差分再生成、監査担当への差分再監査が機能する。
7. 同一セッションの二重確定が拒否される。
8. 中断・再起動後に完了済み工程を重複せず、未完了地点から再開する。
9. 確定台帳から次章の`scene-planner`への引き渡しメールに、確定プロット・確定バイブル・正史・4種台帳のパスが含まれる。
10. `works`テーブルの`next_agent`が次章の`scene-planner`へ正しく更新される。
11. Gemini失敗時に別AIへフォールバックせず、状態とエラーを保持する。
12. ダミーアダプターだけで確定本文入力から台帳確定・次章引き渡しまで完走する。
13. 長文本文・台帳・監査結果でもargv長が本文長に比例せず、本文断片を含まない。
14. 未知セッション、別作品・別章混入、確定前の正史参照を拒否する。
15. 既存のURS、企画、ストーリー設計、本文制作、メール、開発ループ、Geminiの全回帰テストが成功する。

利用可能な環境では次も実行してください。

- Python全体のテスト（`python -m unittest discover -v`）
- `python -m compileall -q kobo mail tests`
- CLIのダミースモーク
- `gemini-doctor`
- 明示的な実Geminiスモークは、非機密の短文に限り1回だけ行ってよい
- `git diff --check`

実Geminiスモークが利用資格や信頼設定で失敗しても、ダミーを含む自動テストが成功していれば実装全体の失敗とはしません。ただし、実応答生成に成功したと偽らず、終了コード、分類、成果物の有無を報告してください。

## 7. 受入条件

- 確定本文だけから正史と5種の台帳を生成・監査・承認・確定できる。
- 次章が直前の承認済み状態（確定プロット・確定バイブル・正史・台帳）を固定参照できる。
- 中断再開しても完了済み工程を重複実行しない。
- 既存のURS、企画、バイブル、プロット、本文、メール、開発ループの全回帰テストが成功する。
- `SPEC.md`を実装結果に合わせて次版へ更新し、要求ID、受入条件、未解決事項、実装済みと未実装の境界を整合させる。
