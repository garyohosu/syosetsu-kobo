# 第一試作を実際に執筆し、読後評価可能な状態まで進める

## 1. 目的

基盤機能の追加を止め、第一作の本文を実際に完成させてください。

この作業の成功基準は、コード、テスト、設計書の完成ではありません。hantaniが本文を読み、「続きを読みたいか」を評価できる状態にすることです。

「既存資料を確認しました」「次に企画を提示します」「その方針で進めます」という報告だけで停止してはいけません。今回の必須成果物は本文です。

## 2. 作業開始前

最初に`AGENTS.md`を全文読み、現在のGit状態と他プロセスを確認してください。

```powershell
git status --short --branch
git log --oneline --decorate -8
```

開始条件:

- `main`と`origin/main`が同期している
- 作業ツリーがclean
- 他のエージェントが同じ作業ツリーを書込み中ではない

リモートに次のファイルが追加済みです。ローカルに無い場合は`git pull --ff-only`で取得してください。

- `novels/prototype-001/READER_PROFILE.v001.md`
- `novels/prototype-001/CONCEPTS.v001.md`
- `novels/prototype-001/SELECTED_CONCEPT.v001.md`

## 3. 必読資料

## 4. 今回の選定企画

第一試作は次で進めてください。

```text
辺境工房の品質管理官――壊れた魔導具より、壊れた仕組みを直します
```

利用者の最終選択前の暫定企画ですが、進行を止めないため第一話試作まで作成します。企画選択確認を理由に停止してはいけません。

## 5. 必須成果物

次を作成してください。

### 5.1 第一話本文

保存先:

```text
novels/prototype-001/CHAPTER-001.v001.md
```

条件:

- 本文5,000〜10,000字
- 目標7,000字前後
- 作品名、章題を付ける
- メタ解説、制作意図、箇条書きを本文へ混ぜない
- `SELECTED_CONCEPT.v001.md`の第一話設計を踏まえる
- 冒頭800字以内に六台の給湯器故障と日没までの期限を示す
- 2,000字以内に主人公リオが独自の仮説を持つ
- ミナの帳面が解決に不可欠である
- 給湯器だけでなく、検査・記録の仕組みも直す
- 工房、食堂、診療所、温かい食事を具体的に描く
- ミナが正式に役割を得る
- 最後に王都で使用禁止となった刻印を示し、次話への疑問を残す

### 5.2 自己監査

保存先:

```text
novels/prototype-001/CHAPTER-001-AUDIT.v001.md
```

次を本文の具体的な箇所とともに評価してください。

1. 冒頭から先を読みたくなるか
2. 主人公の仕事や工夫が具体的か
3. 成果が積み上がる期待があるか
4. 登場人物と共同体に関心を持てるか
5. 世界で暮らしている感覚があるか
6. 説明過多になっていないか
7. 最後に次話を読みたい疑問があるか

各項目を5段階で採点し、弱点と修正候補を記載してください。

### 5.3 利用者評価票

保存先:

```text
novels/prototype-001/READER_FEEDBACK.v001.md
```

利用者が本文を読んだ後に直接記入できる形式にしてください。

最低限:

- 続きを読みたい度 1〜5
- 主人公への関心 1〜5
- ミナへの関心 1〜5
- 仕事・技術描写の面白さ 1〜5
- 日常・食事・拠点の魅力 1〜5
- 説明の長さ 1〜5
- 最も良かった場面
- 退屈した箇所
- 不自然だった箇所
- 次に読みたい内容
- この企画を続ける／別企画を試す

## 6. 本文担当

既存仕様どおり、本文執筆はGemini担当です。実Geminiを使用する場合は、既存の非対話契約、固定参照、UTF-8、成果物の非上書きを守ってください。

Geminiの導入・認証・実行が可能かは、必要に応じて既存doctorまたはsmokeで確認してください。本文生成に失敗した場合、無言で別AIの本文へ置き換えてはいけません。

ただし、Gemini利用不能が判明する前に、さらに設計書、基盤機能、一般的なリファクタリングを追加してはいけません。利用不能の場合は、実行コマンド、エラー分類、生成済みタスク、次の再開操作を記録して停止してください。

## 7. 推敲

本文初稿が生成されたら、既存の`prose-reviewer`または同等の独立監査を使用し、最大1回だけ対象箇所を改稿してください。

今回の試作では、改稿ループを何度も回して完成を遅らせてはいけません。

優先する修正:

- 冒頭が遅い
- 技術説明が講義になっている
- ミナが解決の道具にしか見えない
- 食堂や診療所の困り事が伝わらない
- 解決が主人公の独断だけで進む
- 最後の刻印が唐突または弱い

## 8. 禁止事項

- 新しい基盤機能の追加
- devloopの改造
- メールシステムの一般化
- 正史・台帳工程の追加修正
- 第一話を作らず、読者分析だけを更新して完了扱いすること
- 企画選択の質問だけを出して停止すること
- 1,000字程度の梗概を5,000〜10,000字本文として報告すること
- ダミー成果物を小説本文として報告すること

## 9. 検証

最低限、次を確認してください。

- `CHAPTER-001.v001.md`がUTF-8で非空
- 日本語本文が5,000〜10,000字
- 指定された主要人物、問題、期限、解決、食事、成果、引きが存在
- Markdownのコードフェンス不整合がない
- `git diff --check`成功

文字数はPythonで計測し、結果報告へ記載してください。

## 10. コミットと結果報告

本文、監査、評価票を意味のある単位でコミットし、pushしてください。

結果報告:

```text
instructions/result-20260728-15.md
```

記載項目:

- 本文文字数
- 使用した本文生成担当・モデル
- 生成回数と改稿回数
- 変更ファイル
- 自己監査の7項目得点
- 実行した検証
- コミットSHA
- push結果
- 利用者が最初に読むファイル
- 未解決事項

完了報告では、利用者が最初に読むファイルを明確に次として示してください。

```text
novels/prototype-001/CHAPTER-001.v001.md
```

## 11. 利用枠低下時

`AGENTS.md`に従い、利用枠が25%以下になった場合は新しい工程へ進まず、現在の成果物を保存・検証・コミット・pushしてください。

本文が5,000字未満の場合は完成扱いせず、`wip`として正直に記録してください。
